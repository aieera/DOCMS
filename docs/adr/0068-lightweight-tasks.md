# ADR 0068 — Lightweight Tasks

Date: 2026-05-09
Status: Accepted

## Context

VaultDMS already has `workflow_tasks` ([000001_initial_schema:962](../../services/document/migrations/000001_initial_schema.up.sql#L962))
— rows generated by the workflow service for approval steps. They
have a strict shape (instance_id, step_name, status ∈
pending|approved|rejected|delegated|escalated) bound to a Temporal
workflow.

§10.6 calls for a SECOND, lighter-weight task model:

- "Send Acme contract to legal for review by Friday" — created by a
  user from a document.
- "Doc owner: rotate redaction approval" — created automatically by
  a workflow as a follow-up step that's NOT itself an approval.

Trying to fold both into `workflow_tasks` would either pollute the
approval-step shape (with optional fields most rows don't use) or
require schema-level checks that depend on whether `instance_id` is
NULL. Cleaner: a sibling `tasks` table.

## Decision

### Schema

```sql
CREATE TABLE tasks (
  tenant_id                     UUID NOT NULL REFERENCES organizations(id),
  id                            UUID NOT NULL DEFAULT gen_random_uuid(),
  title                         TEXT NOT NULL,
  description                   TEXT,
  status                        TEXT NOT NULL DEFAULT 'open'
                                  CHECK (status IN ('open','in_progress','done','cancelled')),
  priority                      TEXT NOT NULL DEFAULT 'normal'
                                  CHECK (priority IN ('low','normal','high','urgent')),
  due_at                        TIMESTAMPTZ,
  assignee_id                   UUID,
  -- Linked-resource FKs. Both nullable; a task can be doc-only,
  -- workflow-only, both, or neither (a generic to-do).
  linked_document_id            UUID,
  linked_workflow_instance_id   UUID,
  -- Where the row came from. 'user' = manual create; 'workflow' =
  -- generated by a workflow step that wasn't itself an approval.
  source                        TEXT NOT NULL DEFAULT 'user'
                                  CHECK (source IN ('user','workflow')),
  -- Timestamps + audit
  created_by                    UUID NOT NULL,
  completed_by                  UUID,
  completed_at                  TIMESTAMPTZ,
  -- Notification-state book-keeping. The hourly sweep checks both
  -- flags so a task gets at most one due-soon and one overdue ping.
  reminded_at                   TIMESTAMPTZ,  -- 24h-before-due ping fired
  overdue_notified_at           TIMESTAMPTZ,  -- overdue ping fired
  created_at                    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at                    TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, id),
  FOREIGN KEY (tenant_id, assignee_id) REFERENCES users(tenant_id, id) ON DELETE SET NULL,
  FOREIGN KEY (tenant_id, created_by)  REFERENCES users(tenant_id, id),
  FOREIGN KEY (tenant_id, linked_document_id)          REFERENCES documents(tenant_id, id) ON DELETE SET NULL
);
```

RLS-isolated like every other tenant table. Indexes: `(tenant, assignee, status)`
for the inbox query, `(tenant, status, due_at)` for the sweep,
`(tenant, linked_document_id)` for the doc-detail panel.

### Routes

```
POST   /api/v1/tasks                            — create (any user)
GET    /api/v1/tasks/mine                       — inbox (assigned to me)
GET    /api/v1/tasks?document_id=…              — list by doc (or by query filters)
GET    /api/v1/tasks/{id}
PATCH  /api/v1/tasks/{id}                       — title/desc/due/priority
POST   /api/v1/tasks/{id}/assign  {assignee_id}
POST   /api/v1/tasks/{id}/unassign
POST   /api/v1/tasks/{id}/complete
POST   /api/v1/tasks/{id}/reopen
DELETE /api/v1/tasks/{id}                       — hard delete (creator or admin)
```

### Notifications

Three subjects emitted via the document service's outbox:

| Subject | When | Recipient |
|---|---|---|
| `dms.notify.task.assigned.v1` | inline on assign | new assignee |
| `dms.notify.task.due_soon.v1` | hourly sweep, due within 24h, `reminded_at IS NULL` | assignee |
| `dms.notify.task.overdue.v1`  | hourly sweep, `due_at < now()`, `overdue_notified_at IS NULL` | assignee + creator |

The notification service consumes `dms.notify.>` and emails per its
existing `DeliveryPayload` shape (`tenant_id`, `user_ids`, `title`,
`body`, `resource_type=task`, `resource_id`).

### Sweep

The document service runs an hourly ticker in `cmd/server/main.go`
that scans for crossings:

```sql
-- due_soon
UPDATE tasks SET reminded_at = now()
 WHERE tenant_id = $1
   AND status IN ('open','in_progress')
   AND due_at IS NOT NULL
   AND due_at >= now() AND due_at <= now() + interval '24 hours'
   AND reminded_at IS NULL
RETURNING id, assignee_id;

-- overdue
UPDATE tasks SET overdue_notified_at = now()
 WHERE tenant_id = $1
   AND status IN ('open','in_progress')
   AND due_at IS NOT NULL
   AND due_at < now()
   AND overdue_notified_at IS NULL
RETURNING id, assignee_id;
```

Each returned row triggers an outbox notify event. The flag write
+ event emission happen in one tx so a crash between the two states
doesn't double-fire on next sweep (visible per-row idempotency
guarantees the user gets at most one reminder + one overdue ping
per task).

### Permissions

- **Create**: any authenticated user. The created task is
  visible to the creator, the assignee (if set), and tenant admins.
- **Assign / unassign / complete**: creator OR current assignee OR
  admin/owner.
- **Edit other fields**: creator OR admin/owner.
- **Delete**: creator OR admin/owner. Soft-delete isn't modeled;
  hard delete with audit row.

### Cross-cutting integration

- **Doc detail page** lists tasks linked to the doc + lets you
  create a new one inline.
- **Workflow steps** that need a follow-up to-do (rather than an
  approval signal) call `tasks.Create` with `source=workflow,
  linked_workflow_instance_id=...`. The workflow service does NOT
  read tasks back — it doesn't care if they're done.

## Consequences

- One new table, three new outbox subjects, one ticker. The model
  stays separate from `workflow_tasks` to avoid the optional-field
  pollution the alternative would cause.
- The 24h reminder + overdue alert use single-shot flags
  (`reminded_at`, `overdue_notified_at`). Re-opening a completed
  task does NOT clear them automatically — that's a manual edit if
  the user wants the reminder cycle to run again. Documented in the
  API doc.
- Manual creation is rate-limited at the gateway (existing rule
  applies) but otherwise cheap. Workflow-generated rows are sized
  by workflow throughput; no new constraint here.

## Out of scope

- Subtasks / parent_task_id. Add when a customer asks; keeps the
  schema flat for v1.
- Recurring tasks. Cron-like recurrence belongs in workflow, not
  tasks.
- Task search via the search service. The `/tasks/mine` query is
  enough for v1; index when volumes warrant it.
