# Release Policy

**Owner:** Release engineering / platform
**Applies to:** SeDoc v1.0 onward.

## Versioning

**SemVer 2.0.** `MAJOR.MINOR.PATCH`, incremented by:

- **MAJOR** — breaking changes to the HTTP API, the OpenAPI schema,
  the Helm chart values, or the data model. Breaking changes require
  a deprecation cycle (see below).
- **MINOR** — backwards-compatible features. New endpoints, new
  fields (additive), new chart values with defaults.
- **PATCH** — backwards-compatible fixes. No new endpoints, no new
  required config, no schema migrations that take more than a
  single-digit number of seconds.

Pre-GA builds carry `-rc.N` suffix (`1.0.0-rc.1`). Internal builds
use `+build.<sha>` metadata. Images are tagged with the exact tag
(e.g. `ghcr.io/aieera/sedoc/auth:1.0.0`); `latest` points to the most
recent non-rc release.

## Release cadence

- **Minor release: monthly**, on the first Tuesday of the month.
- **Patch release: as needed**, typically weekly during a minor's
  lifetime. Security patches out-of-band, within SLA (see threat-
  model.md remediation table).
- **Major release: no fixed cadence**, driven by business need and
  deprecation windows.

Every release cuts a `release/vX.Y` branch on the first patch; patch
releases on a minor come from that branch. Main always represents
the next minor.

## Deprecation policy

1. A field, endpoint, or config key is marked **deprecated** in the
   minor release where we intend to remove it in the next major. The
   OpenAPI spec carries `deprecated: true`; the HTTP response carries
   `Deprecation: true` and `Sunset: <RFC-3339>` headers.
2. A deprecation is never introduced and removed in the same major
   line. Minimum two minor releases between deprecation and removal
   (~2 months) in v1.x; for v2.x onward, minimum is one **major**
   cycle.
3. The CHANGELOG lists every deprecation in a dedicated section of
   each minor. The release announcement repeats it.
4. **No silent removals.** If an endpoint disappears from the code
   without having been deprecated in a prior release, that is a bug,
   not a release.

## Supported versions

- **Latest minor + previous minor**: full support (features, fixes,
  security).
- **Older minors**: security-only fixes for 6 months after the next
  minor ships.
- **Older majors**: security-only fixes for 12 months after the next
  major ships. Enterprise-tier customers get extended support under
  contract.

A service bug in an unsupported version gets a backported fix only if
the customer is on enterprise tier with an explicit support clause.

## Artifact signing

Every release artifact is signed with Sigstore cosign (keyless OIDC
via GitHub Actions).

Verify an image:

```bash
cosign verify \
    --certificate-identity-regexp '^https://github.com/raabyt/vaultdms' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    ghcr.io/aieera/sedoc/auth:1.0.0
```

Verify the SBOM attestation:

```bash
cosign verify-attestation --type spdxjson \
    --certificate-identity-regexp '^https://github.com/raabyt/vaultdms' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    ghcr.io/aieera/sedoc/auth:1.0.0
```

Air-gapped bundles are distributed with the SHA256 published in the
release notes. Enterprise customers can request Raabyt-signed bundles
(cosign key-based) or bring-your-own-key signing.

## SBOM

Every service image ships with an SPDX 2.3 JSON SBOM, generated by
Syft during the release workflow and both attached to the GitHub
Release and attested to the image via cosign. SBOMs include:

- Every Go module pulled by `go mod`.
- OS packages in the base image.
- Third-party binaries (ClamAV, Ghostscript, LibreOffice, etc. where
  bundled).

CVE scans against the SBOM are run weekly post-release; results go
to `docs/security/cve-scans/YYYY-MM-DD/` (Wave 14.6b).

## Release checklist

Before tagging `vX.Y.Z`:

- [ ] All Wave 13 CI gates green on the commit being tagged
  (integration, mutation, frontend-e2e, frontend-coverage,
  k6-lint, security-gate).
- [ ] CHANGELOG.md updated with the release section.
- [ ] OpenAPI drift check green (hard-fail once 14.2 backfill
  complete).
- [ ] UPGRADE.md written if any migration, config-rename, or
  deprecation fires.
- [ ] Release notes drafted (see template below).
- [ ] One-off: confirm no feature-flagged incomplete features are
  enabled by default.

After pushing the tag:

- [ ] Verify release workflow finished green — 16 image builds +
  signing + bundle build + GitHub Release.
- [ ] Install the bundle in the staging cluster, run the smoke test
  from `docs/deploy/airgap-install.md`.
- [ ] Post release announcement (product + status page + customer
  email list).
- [ ] Kick off weekly CVE scan.

## Emergency release

Out-of-band patch for a Critical security finding (per threat model):

1. Create `release/vX.Y-emergency-<CVE-ID>` branch off the affected
   release branch.
2. Fix + test. Skip the monthly-cadence gating.
3. Tag `vX.Y.Z+1-emergency` and let release workflow run.
4. Announce via security-disclosure channel (not monthly notes).
5. Backport to all supported minors in parallel PRs.

Emergency-release commits skip non-critical CI gates (mutation,
full chaos suite) but never skip integration, security-gate, or
e2e. Document the skip reason in the PR body.
